## 五、演练发现的一个真实缺陷（已修复）

**这是本任务最重要的产出，也是一个本该留到用户手里才爆发的缺陷。**

### 现象

拉取报告的 `backupPath` 字段返回的是**备份根目录**，而不是真正装着副本的那一层
带时间戳的目录。用户（或界面）照着报告给的路径去回退，会找不到副本。

### 定位

- `src/apply.js:37` 的 `applyPatchFile` 已经正确返回了 `backup` 对象，其中
  `backup.backupPath` 就是真实备份目录；
- 但 `src/service.js:285` 把它丢掉了，改填 `options.backupRoot`——父目录。

```js
// 修复前
backupPath: options?.backupRoot ?? '',
```

### 为什么单元测试没抓到

原 `test/service.test.js:135` 只断言 `report.backupPath` 为真：

```js
assert.ok(report.backupPath, '报告应含备份位置')
```

备份**根目录**当然也为真。这条断言看起来在测备份位置，实际什么都没测到——
典型的「断言写得太弱，绿灯是假的」。

### 修复

改为一并返回真实的 `backupPath` 与备份文件清单，并新增回归测试**比对实际文件是否存在**，
不再只看字段为非空：

```js
assert.notEqual(report.backupPath, join(root, 'backup'), '不能返回备份根目录')
assert.ok(existsSync(join(report.backupPath, join(dshRoot, 'cordis.patch.yml'))))
```

## 七、演练过程中我自己的两次误报（如实记录）

按计划要求，偏差要原样记录。这两次都不是插件的问题，是我的断言写错了，
但**记录它们有价值**：它们说明「跑通了」和「测对了」是两件事。

### 误报一：3 条「本机配置被改动」是假的

第一版断言比的是**原始文本片段**，结果报告 webserver / ui-theme / permission 三处被改动。
逐项排查后确认：重渲染把 `'10.0.0.9'` 写成 `10.0.0.9`，**语义完全相同**，只是引号风格变了。

改成比解析后的值（`deepEqual`）后全部通过。

**教训**：凡是比对配置是否被改动，必须比语义，不能比文本。
本项目已知的代价是注释与格式会变（技术取舍方案 A），因此文本级断言天然会假警报。

### 误报二：「回退失败」也是假的

第二版回退断言拿**拉取后**的内容当期望值。但备份里存的是**拉取前**那份，
回退的意义就是撤销拉取——回退正确反而被判为失败。

改为断言「回退后 ≠ 拉取后」且「公共条目恢复为拉取前那份」后通过。

**教训**：写回退断言前先想清楚「回退到哪个时点」。这个时点判断错了，断言会南辕北辙。

## 十、第一期收尾时发现的遗留缺口（未完成，需决策）

写 Task 16 文档回写时逐条核对开放项，发现**两项被明确排在「第一期实现时」的开放项并未完成**。
如实记录在此，不掩盖。

### 缺口一：读路径的双通道交叉校验没有接进流程（较重要）——**已修复**

**设计决策 24**（用户裁定）要求：读路径以官方接口为主通道、直读文件为校验通道，
两者不一致时停下由用户裁决。设计 §2.3 把它作为读路径的核心安全机制。

**实际状况**：

| 环节 | 状态 |
|---|---|
| `src/skills.js:120` `crossCheckSkills()` | 已实现，有测试 |
| 是否有任何地方调用它 | **没有**。全仓库检索仅命中定义处 |
| `index.js:18` `export const inject = ['settings', 'skills']` | 声明了依赖，但两个服务**从未被使用** |
| `src/service.js` 的 `preparePush` | 只走直读文件一条通道（`readLocalRows()`） |

**这意味着**：主通道（官方接口）实际上没有参与读路径，交叉校验也就无从谈起。
`inject` 声明了一个用不上的依赖——如果官方把某个服务改名或移除，插件会拒绝启动，
但它其实并不需要那个服务。

**为什么现在能跑通**：因为直读通道本身就是可用的，单通道也能产出正确结果。
但这与设计决策 24 不符，且丢掉了「官方接口行为变化时报警而不是静默同步错内容」这层保护。

**严重程度评估**：不影响当前功能正确性，属于**安全网缺失**而非功能缺失。
单元测试与端到端演练都覆盖不到它——因为它们测的是「结果对不对」，而不是「有没有走双通道」。

### 缺口二：开放项 7（Windows 路径处理）未做 ——**已修复**

全仓库检索 `win32`、盘符、反斜杠路径：除 `src/home-paths.js:44` 支持 `~\` 开头的家目录展开外，
**没有任何 Windows 路径处理**。备份目录层级保留了绝对路径（`src/backup.js` 用
`relative('/', file)`），在 Windows 上这会产生含盘符的路径。

**影响**：目前 DSH 的实际使用环境是 Linux/macOS，因此不阻塞。但设计把它排在第一期，
是考虑到配置里存的是绝对路径。若要支持 Windows，备份目录结构与路径处理都需要重新验证。

### 缺口三：开放项 3（裁决界面形态）实际未定 ——**仍未做**

`client.js` 目前只有状态行、跳过项列表与拉取／推送两个按钮，
**没有交叉校验不一致时的裁决界面**。

这个缺口与缺口一相关：裁决界面是服务于交叉校验的，交叉校验没接进去，
界面也就无处可放。两者应一并处理。

### 修复情况（后续补记）

| 缺口 | 状态 | 说明 |
|---|---|---|
| 一 · 交叉校验未接入 | **已修复** | `crossCheckSkills()` 接进 `preparePush`／`preparePull`，并在报告与界面概述里给出提示；`inject` 声明不再有名无实 |
| 二 · Windows 路径 | **已修复** | `src/backup.js` 原写 `relative('/', file)`，而 `win32.relative('/', 'C:\\Users\\…')` 返回的是**绝对路径本身**（两边根不同无法求相对），join 后会生成 `C:\` 这样的嵌套垃圾目录。改用 `parse(file).root` 取该路径自己的根再求相对；`file` 恰为根本身时用 `_root_` 兜住空串 |
| 三 · 裁决界面 | **仍未做** | 交叉校验现在会在不一致时报警，但「停下让用户逐项裁决」的界面还没有 |

缺口二的教训值得单独记一笔：**149 个用例全绿也没照出这个缺陷**，因为所有测试都跑在 POSIX 上，
该分支在 Linux/macOS 上恰好正确。补的三条用例用 `win32` 的纯函数语义验证，不必真在 Windows 上跑。

## 十一、界面接线的验收（后续补记）

用户实装前，先在一台隔离实例上把界面这条链路也验了。新增两步：

| 步骤 | 验什么 |
|---|---|
| 真发一次 HTTP 请求 | 趁进程活着请求 `/api/settings-roam.status`。Connection 层在物理载体上先施加信任策略，不带会话 cookie 一律 401（`packages/client/connection/src/browser-auth.ts:315`），所以脚本照浏览器的做法先经 `/?token=…` 换 cookie 再访问 |
| 真导出一次并去磁盘上看 | 只断言「返回 200」不够：路径解析错了也会返回一份全 0 的合法响应。因此还断言 `patchExists`、profile 名、导出目录都落在我们指定的那个隔离根下，并去磁盘上确认 `manifest.json` 在 |

**过程中照出四个缺陷**，全都是「单元测试全绿、真装载才炸」或「不写测试就看不见」的类型：

| # | 缺陷 | 为什么前面 34 项演练没抓到 |
|---|---|---|
| 1 | `client.js` 只导出一堆组件，没有 `apply` 与 `inject` | 模块加载器会**接受**它，但没有任何东西会去挂载它——设置页一片空白且不报错 |
| 2 | `status` 处理器直接返回对象，而 `route.fetch` 的契约是 `Promise<Response>` | 类型契约在运行时才检查 |
| 3 | `status` 响应缺 `ok` 字段，而界面用 `ok` 判断成败 | 一次成功会被界面当成失败；纯读代码看不出来的接线问题 |
| 4 | `index.js` 直接读 `ctx.pluginManager`，违 Cordis 的 DI 纪律 | 报 `cannot get property "pluginManager" without inject`，导出整条路径 500。前四步真装载验收全绿推不出第五步能过 |

第 4 条与 Task 14 那三个缺陷是同一类：**在普通 Node 里最自然的写法，在 Cordis 里是明确禁止的**。
这类问题如果不在真装配环境里跑一次，会一直潜伏到用户安装时才爆发。为此新增
`test/apply-host.test.js`（12 例）：用一个「读未注入属性就抛错」的假 ctx 把这条纪律固化下来，
不必每次启动 DSH 才能发现。

## 十二、界面实装核对（用户报告「很丑、点了没反应」之后）

用户装上后反馈：设置页很丑，而且点完没什么反应。用真浏览器（`scripts/ui-preview.mjs` 起的隔离实例，
不碰用户正在用的 profile）复现，确认两件事都成立，并各定位到根因。

### 12.1 「很丑」：没有用宿主的设计系统

复现截图里整节是裸 `div` 加浏览器默认样式的 `<button>`（灰底、2px 凸起边框、极小字号），
而旁边的官方分区用的是 CSS Module 类名。原因是 `client.js` 自己用 `h('div')`／`h('button')` 糊界面。

修法：改用宿主的 `@deepseek-ai/dsh-client-ui-primitives`（它已在 web bundle 的 boot manifest 里，
`require` 能解析到），并注入一张只用 `--dsw-*` 令牌的样式表。令牌来源是官方的
`packages/client/ui-theme/src/styles/design-platform.css`；`packages/client/ui-settings-models/src/client/ModelsSection.module.css`
的文件头明确警告：裸 `--border`／`--surface`／`--text-*` 在本应用里无定义，会落到浅色字面量 fallback
并在深色主题下仍是浅色。取值前逐个 grep 过，没有照抄名字凭印象写。

### 12.2 「点了没反应」：三处独立的接线错误

| # | 缺陷 | 表现 | 为什么看不见 |
|---|---|---|---|
| 1 | 配置表单**不会**自动出现 | 用户没有地方填仓库地址，按钮永远停在「还没配置云端仓库」 | 装了 `Config` schema 只让条目出现在 `ctx.settings.describe()` 里。官方设置外壳不给分区内容画任何 chrome（`packages/client/ui-settings-general/src/client/shell-contract.ts:24-28` 只传 `{id, order, label}`），全仓库也没有任何「schema → 表单」渲染器。表单必须插件自己接 `ctx.configForms` 画 |
| 2 | `exports.inject` 写成了函数 | 浏览器里挂不上，单元测试与真装载都照样通过 | 官方一律是**字符串数组**（`packages/client/ui-settings-plugins/src/client/index.ts:28` `export const inject = ['slots','locale']`），它声明「要用到哪些客户端服务」，由注入器在挂载前解析。模块加载器会**接受**一个函数，只是拿不到依赖声明 |
| 3 | `locale/*.json` 写了却从未登记 | 分区标题退化成键名 | 没有任何地方调 `ctx.locale.register`。官方写法是 `ctx.locale.bind(NS)` + `ctx.effect(() => ctx.locale.register(NS, {zh, en}), …)` |

附带一条：宿主语言服务查的是**扁平键**（`packages/client/locale/src/client/index.ts` 的 `lookup` 直接 `dict[key]`，不做点号下钻），
所以登记前要 flatten 一次；嵌套结构只留给宿主侧插件清单读 `meta.title`／`meta.description` 用。

### 12.3 保存之后界面不刷新（用户第二次反馈的「点完没反应」）

预览实例里填上仓库地址并失焦，配置确实写进了 `cordis.patch.yml`（绿色「已保存。」也出现了），
但状态行仍显示「还没配置云端仓库」、两颗按钮仍是禁用——因为 `SectionContainer` 只在挂载时取过一次状态。
用户看到的是「已保存」和两个点不动的按钮并存，合理结论就是「保存没生效」。

修法：`ConfigCard` 提交成功后回调 `onSaved`，由 `SectionContainer` 重新取一次状态
（写配置会让宿主重新组合插件，新地址要等这一轮走完才反映到状态里，所以立刻取一次、1.2 秒后再取一次）。
反向对照也锁进了测试：写入被拒时不得刷新——那会让界面显示「宿主已接受」，而实际什么都没落盘。

### 12.4 两个验收脚本自身的缺陷（比插件的缺陷更值得记）

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | `verify-load.mjs` 先手写 manifest 的 `link:` 依赖，再调 `dsh plugin add` | `plugin add` 只在「依赖名在装之前不存在」时才把它追加进 `dsh.profile.bundles`（`packages/boot/plugin-manager/src/operations.ts:93` `if (beforeDeps.has(name)) continue`），于是插件既不进 bundles 也不进组合树。**一个由验收脚本自己制造的假故障，看起来却像插件坏了** |
| 2 | `verify-load.mjs` 不传 `--port` | DSH 的缺省端口是 3080（`packages/bundle/web-app/cordis.patch.yml:184` `ctx.webStartup.port ?? 3080`），而本机可能正有实例在监听同一端口。实测那一次验收请求打到了另一个实例上，返回 404；更坏的情况下会**往别人的数据根里写导出文件**。已改为先用 `node:net` 要一个空闲端口再显式传入 |

这两条与插件代码无关，但它们说明一件事：**验收脚本本身也是被测对象**。
一个会打到别的实例上的脚本，给出的结论比没有验收更危险——它看起来是通过或失败得有理由，
实际量的是别的东西。

## 十三、第二阶段（本地导入导出）的实装核对

第二阶段的入口与第一阶段相反：**不依赖云端仓库**。用户换台机器把配置弄回来，不该先要求他有一个远端仓库。

### 13.1 一次「保存了但不生效」的假象

在隔离实例里把「导入目录」填成一个真实导出包，输入框显示新值、绿色「已保存。」出现、`cordis.patch.yml` 里也确实写进了 `importRoot`——
然后点「导入」，界面仍然去默认目录找包，报「读不到这个目录」。

根因不是保存失败，是**保存成功但服务层没用上新值**：

- DSH 改配置是**原地更新运行中的 `config` 对象**（`packages/boot/config-editor/src/index.ts:104` 在写盘之前就调 `resolveConfig(fiber.runtime, resolved)`），**插件不会被重新 apply**。
- 而 `createSyncService` 原先在装配时把 `exportRoot`／`importRoot`／`profileName` 拷成了常量。常量不会变，于是行为永远停在装配那一刻。

为什么这个缺陷很难被抓住：单元测试把配置当参数传（当然是对的），真装载验收只验「表单出现、路由 200、导出能落盘」，
**没有任何一处在「运行中改配置，然后看行为有没有跟着变」**。只有真去用一次才看得出来。

修法：把 `config` 对象本身交给服务层，用的时候现读（`readOption`），不再存快照。回归用例锁死「改了选项，服务必须立刻用上新值」。

> 附带一个反直觉的现象：`configured`（有没有配仓库地址）当时**是**实时变化的，
> 因为它每次调用都去懒构造后端、顺带读了配置。
> 也就是说同一份配置里，有的选项算对了、有的算错了——这比整块都错更容易骗过人。

### 13.2 导入动作在真浏览器里的核对

| 步骤 | 观察到的结果 |
|---|---|
| 填导入目录并失焦 | `cordis.patch.yml` 写入 `importRoot`；状态里 `available: true`、`fileCount: 2` |
| 点「导入」 | 出现待确认区：「本次将导入 1 配置项 / 1 技能文件 / 2 本机项（不写回）」+ 来源包路径 + 「这些项留在了本机」逐条说明 |
| **确认之前** | 本机配置文件字节未变（单元测试与演练脚本都锁了这条） |
| 点「确认导入」 | 结果卡「本次导入结果 2 / 已写入」；`profiles/ui/cordis.patch.yml` 里出现 `llm-pi-ai` 条目；`skills/demo-skill/SKILL.md` 落到磁盘 |
| 本机项是否被换掉 | 没有。包里的 `webserver(host: 10.0.0.7)` 与 `ui-theme` 被拒绝，本机自己的条目原样保留 |

### 13.3 预览脚本自己制造过两次假故障

`scripts/ui-preview.mjs` 在「插件已在 `dsh.profile.bundles` 里」时，曾把 profile 的 `cordis.patch.yml` 整个写成 `[]`——
于是**在界面上填过的设置会被下一次启动抹掉**，「填好设置 → 重启 → 看生效没」这条最需要验的路根本走不通，
而症状看起来像插件没保存。现在改为：只清掉本插件可能重复的那一条，其余内容原样保留。

（更早的一次假故障：脚本额外手写 `insert` 造成重复注册，写入被判成
「is overridden by a home patch or command-line overlay」。两次都出在同一个脚本上。）

## 十四、第三阶段：真实远端仓库上的往返

前两阶段的演练全部跑在本地裸库上，不走网络。这一节记录第一次**真实云端**往返。

| 项目 | 内容 |
|---|---|
| 仓库 | 用户提供的一个私有库（地址不写进仓库） |
| 分支 | `settings-roam`，首次推送时自动创建，且是孤儿分支 |
| 认证 | 系统 git 的 credential helper（本机是 `gh`），插件代码里没有任何密钥 |

### 14.1 实测链路

1. 机器 A（临时数据根，配置里含 `webserver.host=10.0.0.7`、`ui-theme=dark`、公共项 `llm-pi-ai`，以及一个技能）执行 `push`：
   预览列出 3 个文件 → 加 `--yes` → 远端出现 `refs/heads/settings-roam`。
2. 把那条分支单独克隆下来核对：文件只有 `config/profile.patch.yml`、`skills/demo-skill/SKILL.md`、`snapshot.json`；
   `git merge-base main settings-roam` 为空——**确认是孤儿分支**，没有把别人分支的内容带进来。
3. 机器 B（临时数据根，配置里是 `webserver.host=10.0.0.9`、`ui-theme=light`）执行 `pull`：
   应用 2 项（公共配置 + 技能），B 自己的监听地址与主题保持原值，
   报告给出「本机偏好不会随行」「需要在每台机器上各自配 `OPENCODE_GO_API_KEY`」「需要重启」与备份路径。

### 14.2 这一轮照出来的三个真缺陷

| # | 缺陷 | 后果 | 修法 |
|---|---|---|---|
| 1 | 拉取只读了配置，技能一个都没读 | 供应商定义回来了、技能没回来，而报告里一字未提——看起来像技能本来就不同步 | 从云端快照清单里读出 `skills/` 开头的条目并逐个取回，复用导入侧的 `applySkillFiles`（含可执行位与写前备份）。后端接口保持不变：仍然只有五个动作，不需要「列目录」 |
| 2 | 预览里的「删除 N」把本机独有项算了进去 | 如果点下去会删本机的配置——而本程序从不删除本机的东西。用户据此不敢点，或者点了之后发现没删而困惑 | 预览与计数都只算「新增 + 修改」；本机独有项单独一行写明「本机独有，不会删除」 |
| 3 | 后端会落在仓库的默认分支上 | 同一个人用一个库放多个插件的备份时，两个插件会互相把对方的文件当成「云端多出来的东西」 | 固定占一条自己的分支，且是孤儿分支（见 README 同名小节） |

> 缺陷 1 与缺陷 2 都是**单元测试与既有演练都照不出来**的那一类：
> 前者要「真有一份云端技能」才看得见，后者要「真去看一眼输出」才看得见。
