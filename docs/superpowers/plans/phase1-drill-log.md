## 五、演练发现的一个真实缺陷（已修复）

**这是本任务最重要的产出，也是一个本该留到用户手里才爆发的缺陷。**

### 现象

拉取报告的 `backupPath` 字段返回的是**备份根目录**，而不是真正装着副本的那一层
带时间戳的目录。用户（或界面）照着报告给的路径去回退，会找不到副本。

### 定位

- `src/apply.js:37` 的 `applyPatchFile` 已经正确返回了 `backup` 对象，其中
  `backup.backupPath` 就是真实备份目录；
- 但 `src/service.js:285` 把它丢掉了，改填 `options.backupRoot`——父目录。

```js
// 修复前
backupPath: options?.backupRoot ?? '',
```

### 为什么单元测试没抓到

原 `test/service.test.js:135` 只断言 `report.backupPath` 为真：

```js
assert.ok(report.backupPath, '报告应含备份位置')
```

备份**根目录**当然也为真。这条断言看起来在测备份位置，实际什么都没测到——
典型的「断言写得太弱，绿灯是假的」。

### 修复

改为一并返回真实的 `backupPath` 与备份文件清单，并新增回归测试**比对实际文件是否存在**，
不再只看字段为非空：

```js
assert.notEqual(report.backupPath, join(root, 'backup'), '不能返回备份根目录')
assert.ok(existsSync(join(report.backupPath, join(dshRoot, 'cordis.patch.yml'))))
```

## 七、演练过程中我自己的两次误报（如实记录）

按计划要求，偏差要原样记录。这两次都不是插件的问题，是我的断言写错了，
但**记录它们有价值**：它们说明「跑通了」和「测对了」是两件事。

### 误报一：3 条「本机配置被改动」是假的

第一版断言比的是**原始文本片段**，结果报告 webserver / ui-theme / permission 三处被改动。
逐项排查后确认：重渲染把 `'10.0.0.9'` 写成 `10.0.0.9`，**语义完全相同**，只是引号风格变了。

改成比解析后的值（`deepEqual`）后全部通过。

**教训**：凡是比对配置是否被改动，必须比语义，不能比文本。
本项目已知的代价是注释与格式会变（技术取舍方案 A），因此文本级断言天然会假警报。

### 误报二：「回退失败」也是假的

第二版回退断言拿**拉取后**的内容当期望值。但备份里存的是**拉取前**那份，
回退的意义就是撤销拉取——回退正确反而被判为失败。

改为断言「回退后 ≠ 拉取后」且「公共条目恢复为拉取前那份」后通过。

**教训**：写回退断言前先想清楚「回退到哪个时点」。这个时点判断错了，断言会南辕北辙。

**最重要的一条**：演练证明了「配置值不会跨机器漂移」，但**没有证明「从机 B 能把插件也装上」**。
后者依赖 bundles 名单驱动安装，属于第二期范围。第一期交付的是**配置同步**，
不是**环境复制**。这一点必须在 README 里说清楚，避免用户误解。
