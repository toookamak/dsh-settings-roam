## 一、这份草案要解决什么

第一期收尾时逐条核对设计文档的开放项，发现**四处已实现但未接入**或**已排期但未做**的工作。
它们不影响主流程，但都属于「设计说了、代码没做」的状态，不处理会持续误导后续开发。

按性质分两类：

| 类别 | 内容 | 为什么必须处理 |
|---|---|---|
| **接线缺失** | 功能已实现、有测试，但没有任何地方调用 | 代码看起来完备，实际是死代码；测试绿灯会给人虚假安全感 |
| **排期未做** | 设计明确排在第一期，收尾时未做 | 设计文档与实现不一致 |

**这类缺口单元测试和端到端演练都抓不到**——它们测的是「结果对不对」，
而不是「设计里的机制有没有接上」。只有逐条核对设计决策才能发现。

## 二、四处遗留缺口（第一期收尾盘点）

### 缺口 A：读路径的双通道交叉校验未接入 —— 较重要

**设计依据**：决策 24（用户裁定）、§2.3、§7.2 开放项 2 已关闭

**设计要求**：读路径以官方接口（`ctx.settings.describe()`、`ctx.skills.snapshot()`）为主通道，
直读文件为校验通道，两者不一致时停下由用户裁决。

**实际状况**：

| 环节 | 状态 |
|---|---|
| `src/skills.js:120` `crossCheckSkills()` | 已实现，有测试 |
| 调用点 | **零**。全仓库检索仅命中定义处 |
| `index.js:18` `export const inject = ['settings', 'skills']` | 声明了依赖，两个服务从未使用 |
| `src/service.js` `preparePush` | 只走直读文件单通道（`readLocalRows()`） |

**后果**：
1. 主通道从未参与读路径，交叉校验无从谈起；
2. 丢掉了「官方接口行为变化时报警，而非静默同步错内容」这层保护（设计 §2.3 第 141 行）；
3. `inject` 声明了用不上的依赖——官方若改动这两个服务名，插件会拒绝启动，但它其实并不需要。

**严重程度**：不影响当前功能正确性。**安全网缺失，不是功能缺失。**

### 缺口 B：裁决界面未做

**设计依据**：§7.2 开放项 3、§7.3 界面决策 U1-U3

**实际状况**：`client.js` 只有状态行、跳过项列表、拉取／推送两个按钮，
没有「交叉校验不一致时逐项裁决」的界面。

**与缺口 A 的关系**：裁决界面本就是**为交叉校验服务的**。A 不做，B 无处安放；两者必须一并处理。

**需要用户决定的**：裁决形态——侧边栏主面板里逐项选，还是弹窗统一裁决（开放项 3 原文）。

### 缺口 C：Windows 路径处理未做

**设计依据**：§7.2 开放项 7，明确排在「第一期实现时」

**实际状况**：全仓库检索 `win32`、盘符、反斜杠路径，
除 `src/home-paths.js:44` 支持 `~\` 开头的家目录展开外，**没有任何 Windows 路径处理**。

**具体风险点**：
- `src/backup.js` 用 `relative('/', file)` 保留绝对路径层级，在 Windows 上会产生含盘符的路径
- 配置里的绝对路径在跨平台搬运时的语义问题

**严重程度**：当前实际使用环境是 Linux/macOS，**不阻塞**。

### 缺口 D：插件名单未被收集（新发现）

**设计依据**：决策 22 与 §3.3（插件重装）

**实际状况**：

| 环节 | 状态 |
|---|---|
| `src/bundles.js:62` `collectBundles(pluginManager)` | 已实现，有测试 |
| 调用点 | **零**。全仓库检索仅命中定义处 |
| `index.js` 是否注入 pluginManager | **否**——`grep pluginManager index.js` 无输出 |
| `preparePush` 的 `bundles` 参数 | 由调用方传入；但 `index.js` 装配时无人收集 |

**后果**：`config/bundles.json` 实际上永远不会被真实数据填充。
第一期的「插件只记名字」设计，在运行时是**空的**。

**与已记录的边界关系**：演练记录第十节已说明「第一期交付配置同步、不是环境复制」，
插件驱动安装属第二期。但**连「记名字」这一步都未生效**，比当初的认知更靠前一步——
这一点是本次盘点新发现的。

## 三、第二期范围建议

综合设计 §3.5 的分期表与上述缺口，建议第二期包含四块：

| 编号 | 工作 | 来源 | 依赖 |
|---|---|---|---|
| **P1** | 接入双通道交叉校验 + 裁决界面 | 缺口 A + B | 需先定裁决形态（见第四节） |
| **P2** | WebDAV 介质 | 设计 §3.5 第二期原文 | 后端接口已就绪，改动面小 |
| **P3** | 插件名单收集 + 驱动安装 | 缺口 D + 设计决策 22 | 需实测官方安装接口 |
| **P4** | Windows 路径处理 | 缺口 C | 需 Windows 环境验证 |

**建议优先级**：P1 → P3 → P2 → P4

理由：
- **P1 最前**：涉及用户已裁定的决策，且是安全网；补上后 `inject` 声明的依赖才名副其实。
- **P3 次之**：缺口 D 意味着第一期的「插件记名字」在运行时是空的——
  这是**承诺了却没兑现**的部分，比新增介质更接近「把事情做完」。
- **P2 再次**：设计原文说「同步逻辑一行不改」，后端接口已抽出 5 个方法，
  是四块里最独立的。
- **P4 最后**：当前环境不阻塞，且需要 Windows 机器才能真验证。

## 四、需要用户先决定的事

| # | 决定项 | 影响 |
|---|---|---|
| 1 | 四处缺口是否都进第二期，还是有要先补的 | 决定 P1-P4 的范围 |
| 2 | 裁决界面的形态（侧边栏逐项选 / 弹窗统一裁决） | P1 的设计前提 |
| 3 | 是否要驱动插件安装（P3），还是只把名字记全 | P3 的规模差异很大 |
| 4 | 是否要支持 Windows（P4） | 决定 P4 是否做 |

**第 3 项值得单独说明**：把名字记全只需接入 `collectBundles`，
工作量小；而「驱动官方安装流程把插件真的装上」需要调用官方安装接口，
涉及兼容检查、失败处理、进度反馈，规模大得多，且需要实测确认接口行为。
设计决策 22 说的是后者，但可以拆成两步交付。
